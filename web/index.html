Consensus that survives a network broken in one direction.

Raft and Paxos quietly assume that if A can reach B, B can reach A. Across clouds that assumption breaks — asymmetric routing, one-way security-group rules and half-open NAT state all produce links that work in exactly one direction. The result is not a crash. It is a livelock: a node campaigns forever, deposing a healthy leader on every attempt, while every health check reports green.

Nothing here is pre-recorded. The Go consensus engine — real Ed25519 signatures, real leader election, real hash-chained logs — is compiled to WebAssembly and executing in your browser right now. What actually breaks

Standard consensus is crash-fault tolerant: it assumes a node either works or stops. A one-way link violates that model without any node failing. The classic symptom is the disruptive server — a replica that can send but not receive campaigns endlessly, incrementing its term each round and forcing a healthy leader to stand down, forever.

Two known mitigations exist and etcd ships both: PreVote, a non-binding straw poll that does not increment anyone's term (Ongaro's Raft thesis §9.6), and CheckQuorum, which makes a leader step down once it stops hearing from a majority. Switch to + prevote above and watch the term counter go flat.

Measured finding, reported as found: under this fault, PreVote alone already fixes the livelock. Baseline logs 30 term bumps in 300 ticks; PreVote logs 1; CrossFault also logs 1. CrossFault does not beat PreVote here — it matches it, and adds a different capability: relaying. Claiming otherwise would be easy and dishonest, so the numbers are printed exactly as the test suite produces them.

What CrossFault adds

PreVote makes a badly-connected node harmless. It does not make it useful, and it does not recover the lost link. CrossFault tracks reachability as a directed graph rather than a single number, which enables two things PreVote cannot do: a node with one-way connectivity declines to campaign at all (rather than campaigning and losing), and messages are relayed through a third node around the broken edge — the approach proposed in Toward a Generic Fault Tolerance Technique for Partial Network Partitioning (OSDI '20).

Why there is no BFT here

A hostile transit path is not a Byzantine fault, and conflating the two is the most common error in this problem space. Byzantine fault tolerance is for when a node is compromised and lies. Tampering on the wire is a different, cheaper problem.

Every message here is signed end-to-end with Ed25519 by the sending node, and verified before it can touch consensus state. TLS does not solve this, because TLS is hop-by-hop and terminates at cloud load balancers and API gateways, which then see plaintext. Google's ALTS exists for exactly this reason.

The consequence is the whole argument: an attacker who fully controls the wire can only destroy a message, never forge one. Destruction is an omission — a fault class crash-fault-tolerant consensus already handles. Hit corrupt a link and watch the rejection counter climb while the log stays clean. No 3f+1 replicas, no proof-of-stake, no seconds-long finality.

What signing does not buy: protection from a genuinely compromised node, which holds a valid key and can sign whatever it likes. That needs accountability — making equivocation provable and attributable, in the spirit of PeerReview (SOSP '07) — which is the next layer, and is not yet built here.
